01

Cel i zakres projektu

MELLIS to sklep internetowy rodzinnej pasieki (50 uli, okolice Bolimowskiego Parku Krajobrazowego) sprzedającej miód w trzech wielkościach słoika. Celem jest wdrożenie sprzedaży online z płatnościami i automatyczną wysyłką, przy zachowaniu butikowego, premium charakteru marki.

Zakres MVP (pierwsze wdrożenie)

  • Katalog produktów — 6 odmian miodu, każda w 3 wariantach wielkości (250 g / 500 g / 900 g).
  • Koszyk i checkout — wielokrokowy proces zamówienia (dostawa → dane → płatność).
  • Płatności online — BLIK, karta, szybki przelew. Architektura przygotowana pod Stripe lub Przelewy24.
  • Dostawa — Paczkomat InPost, kurier, bezpłatny odbiór osobisty z pasieki.
  • Treści — sekcja „O nas", galeria, dziennik/blog, opinie klientów, zapis do newslettera.
  • Panel administracyjny — zarządzanie produktami, stanami magazynowymi, zamówieniami i treścią bloga.

Poza zakresem MVP (do rozważenia później)

  • Konta klientów i historia zamówień (MVP może działać jako „guest checkout").
  • Programy lojalnościowe, kody rabatowe, zestawy prezentowe konfigurowalne.
  • Wersja anglojęzyczna (obecnie tylko PL).
  • Integracja z księgowością / fakturowaniem (np. Fakturownia, wFirma).
Załączony prototyp (MELLIS.html) to klikalny, wysokiej wierności wzorzec wyglądu i przepływów — należy traktować go jako źródło prawdy dla UI. Zawiera 3 warianty strony głównej (przełączane w panelu Tweaks) do wyboru kierunku graficznego.
02

Rekomendowany stack technologiczny

Dwie ścieżki. Ścieżka A — gotowa platforma, szybkie i tanie uruchomienie. Ścieżka B — własna aplikacja, pełna kontrola i unikalny wygląd zgodny z prototypem.

Ścieżka A — gotowa platforma (najszybciej)

Dla minimalnego nakładu i kosztu utrzymania. Wymaga akceptacji ograniczeń motywu graficznego.

  • Shopify lub WooCommerce (WordPress) — wbudowane płatności, dostawa, panel.
  • W Polsce dobrze wspierane: Przelewy24, InPost, BaseLinker do automatyzacji.
  • Prototyp MELLIS przekładamy na motyw (theme) — kolory, typografia i układ jako punkt wyjścia.

Ścieżka B — własna aplikacja (rekomendowana dla pełnej wierności prototypowi)

Frontend
Next.js (React)

App Router, SSR/SSG dla SEO. Prototyp jest już w React — komponenty przenosimy 1:1. Stylowanie: CSS Modules / Tailwind z tokenami z prototypu.

Backend / API
Next.js API Routes lub Node (NestJS)

REST lub tRPC. Logika koszyka, zamówień, webhooki płatności i wysyłki.

Baza danych
PostgreSQL + Prisma

Relacyjna, idealna dla zamówień. Prisma jako ORM (migracje, typowanie). Hosting: Supabase / Neon / Railway.

Płatności
Stripe lub Przelewy24

Stripe = najlepszy DX i obsługa kart + BLIK. Przelewy24 = lepsza lokalna obsługa BLIK/przelewów PL.

Hosting
Vercel

Natywny dla Next.js, automatyczny CI/CD z Git, certyfikat SSL, CDN. Alternatywa: własny VPS.

Media / zdjęcia
Cloudinary / Vercel Blob

Optymalizacja i serwowanie zdjęć słoików i pasieki. Prototyp używa placeholderów do podmiany.

CMS treści
Sanity / Payload

Dla bloga „Dziennik" i sekcji edytowalnych — właściciel dodaje wpisy bez kodu.

E-mail transakcyjny
Resend / Postmark

Potwierdzenia zamówień, statusy wysyłki. Newsletter: MailerLite / Brevo.

Rekomendacja: Ścieżka B (Next.js + PostgreSQL + Stripe/Przelewy24 + Vercel). Daje 100% zgodności z prototypem, dobre SEO i niskie koszty hostingu przy obecnej skali, a jednocześnie skaluje się wraz z rozwojem pasieki.
03

Architektura systemu

Przepływ danych między przeglądarką klienta, serwerem aplikacji, bazą oraz usługami zewnętrznymi (płatności, wysyłka, e-mail).

# Przepływ wysokopoziomowy

  Przeglądarka (Next.js, React)
        │  REST / tRPC
        ▼
  Serwer aplikacji (API)  ──────►  PostgreSQL  (produkty, zamówienia, treści)
        │
        ├──►  Stripe / Przelewy24   (sesja płatności + webhook potwierdzenia)
        ├──►  InPost / Furgonetka API (utworzenie przesyłki, etykieta, tracking)
        ├──►  Resend / Postmark      (e-mail potwierdzający + status)
        └──►  Sanity / Payload CMS    (wpisy bloga, edytowalne treści)

  Panel admina (chroniony) ──►  ten sam serwer API + baza

Kluczowe zasady

  • Cena liczona po stronie serwera. Nigdy nie ufamy cenie z przeglądarki — przy tworzeniu zamówienia backend przelicza sumę na podstawie wariantów z bazy.
  • Płatność potwierdzana webhookiem. Zamówienie zmienia status na „opłacone" dopiero po asynchronicznym webhooku od operatora płatności, nie po powrocie użytkownika na stronę.
  • Rezerwacja stanu magazynowego przy składaniu zamówienia, zwolnienie przy nieudanej/porzuconej płatności.
04

Model danych

Główne encje i relacje. Produkt (odmiana miodu) ma wiele wariantów (wielkości słoika). Zamówienie zawiera pozycje, każda wskazująca konkretny wariant z ceną zamrożoną w chwili zakupu.

EncjaNajważniejsze polaRelacje
Productid, slug, name, tagline, description, season, color, notes[], pairing, isBestseller, isActivema wiele Variant, ProductImage
Variantid, productId, size (s/m/l), label, weightGrams, priceGrosze, stock, skunależy do Product
ProductImageid, productId, url, alt, positionnależy do Product
Orderid, number (MEL-XXXX), status, email, phone, subtotalGrosze, shippingGrosze, totalGrosze, deliveryMethod, paymentProvider, paymentStatus, createdAtma wiele OrderItem, ma jeden ShippingAddress
OrderItemid, orderId, variantId, productName, variantLabel, unitPriceGrosze, quantitynależy do Order
ShippingAddressid, orderId, fullName, street, city, zip, parcelLockerCodenależy do Order
BlogPostid, slug, title, category, excerpt, body, coverUrl, readMinutes, publishedAt—
Reviewid, productId?, authorName, city, rating, text, isApprovedopcjonalnie do Product
NewsletterSubscriberid, email, confirmedAt, createdAt—
Kwoty w groszach (integer). Wszystkie ceny przechowujemy jako liczby całkowite w groszach (np. 60 zł = 6000), aby uniknąć błędów zaokrągleń liczb zmiennoprzecinkowych. Ceny startowe: mały 250 g = 3000, średni 500 g = 4500, duży 900 g = 6000.

Szkic schematu (Prisma)

model Product {
  id          String    @id @default(cuid())
  slug        String    @unique
  name        String
  tagline     String
  description String
  season      String
  color       String    // hex motywu słoika
  notes       String[]
  pairing     String
  isBestseller Boolean  @default(false)
  isActive    Boolean   @default(true)
  variants    Variant[]
  images      ProductImage[]
}

model Variant {
  id          String   @id @default(cuid())
  product     Product  @relation(fields: [productId], references: [id])
  productId   String
  size        String   // "s" | "m" | "l"
  label       String   // "Mały" | "Średni" | "Duży"
  weightGrams Int
  priceGrosze Int
  stock       Int      @default(0)
  sku         String   @unique
}

model Order {
  id            String   @id @default(cuid())
  number        String   @unique
  status        String   // new | paid | packed | shipped | done | cancelled
  email         String
  phone         String
  items         OrderItem[]
  address       ShippingAddress?
  subtotalGrosze Int
  shippingGrosze Int
  totalGrosze    Int
  deliveryMethod String  // paczkomat | kurier | odbior
  paymentProvider String // stripe | przelewy24
  paymentStatus String   // pending | paid | failed
  paymentRef    String?  // id sesji u operatora
  createdAt     DateTime @default(now())
}
05

API — punkty końcowe

Minimalny zestaw REST dla MVP. Endpointy publiczne (sklep) oraz chronione (panel admina, autoryzacja sesją/tokenem).

Publiczne — katalog i treści

GET/api/productsLista aktywnych produktów z wariantami i ceną „od".
GET/api/products/:slugSzczegóły odmiany miodu + warianty + zdjęcia.
GET/api/postsWpisy bloga „Dziennik".
GET/api/reviewsZatwierdzone opinie klientów.
POST/api/newsletterZapis e-maila do newslettera (double opt-in).

Publiczne — zamówienie i płatność

POST/api/checkout/quotePrzyjmuje koszyk + metodę dostawy, zwraca przeliczoną sumę (subtotal, dostawa, total, próg darmowej wysyłki).
POST/api/ordersTworzy zamówienie (status new), rezerwuje stan, zwraca orderId + URL/sekret sesji płatności.
GET/api/orders/:numberStatus zamówienia (strona potwierdzenia / śledzenie).
POST/api/webhooks/paymentWebhook od Stripe/Przelewy24 — ustawia paymentStatus=paid, wysyła e-mail, inicjuje przesyłkę.

Chronione — panel administracyjny

POST PATCH DEL/api/admin/products…CRUD produktów i wariantów, ustawianie stanów i cen.
GET PATCH/api/admin/orders…Lista zamówień, zmiana statusu, generowanie etykiety wysyłki.
POST PATCH/api/admin/posts…Zarządzanie wpisami bloga (jeśli bez zewnętrznego CMS).
Walidacja po stronie serwera obowiązkowa. /api/orders ignoruje ceny z żądania — pobiera aktualne priceGrosze wariantów z bazy i sam liczy sumę. Chroni przed manipulacją ceną w przeglądarce.
06

Płatności — Stripe / Przelewy24

Architektura jest niezależna od operatora — wystarczy implementacja jednego interfejsu PaymentProvider. Poniżej przepływ na przykładzie Stripe Checkout; dla Przelewy24 logika jest analogiczna.

Przepływ płatności

  1. Klient klika „Zapłać" → frontend wysyła koszyk do POST /api/orders.
  2. Backend tworzy zamówienie (new), przelicza kwotę, rezerwuje stany i tworzy sesję płatności u operatora.
  3. Backend zwraca URL przekierowania (Stripe Checkout) lub sekret do widgetu (BLIK/Przelewy24).
  4. Klient finalizuje płatność u operatora (karta / BLIK / przelew).
  5. Operator wywołuje webhook POST /api/webhooks/payment (zweryfikowany podpisem) → status paid.
  6. Backend wysyła e-mail potwierdzający i (dla kuriera/paczkomatu) tworzy przesyłkę.
  7. Klient wraca na stronę potwierdzenia (ekran „Dziękujemy za zamówienie" z prototypu).

Szkic — utworzenie sesji Stripe

// POST /api/orders — fragment
const order = await db.order.create({ /* status: "new", pozycje, kwoty */ });

const session = await stripe.checkout.sessions.create({
  mode: "payment",
  currency: "pln",
  payment_method_types: ["card", "blik", "p24"],
  line_items: order.items.map(toStripeLineItem),
  success_url: `https://mellis.pl/zamowienie/${order.number}`,
  cancel_url:  `https://mellis.pl/koszyk`,
  metadata: { orderId: order.id },
});
return { orderId: order.id, checkoutUrl: session.url };
BLIK i Przelewy24 dla rynku PL. Stripe obsługuje BLIK i P24 natywnie w PLN — w wielu przypadkach wystarczy jeden operator. Jeśli priorytetem są niższe prowizje i lokalne wsparcie, rozważ Przelewy24/Autopay jako głównego operatora. Interfejs PaymentProvider pozwala podmienić go bez zmian w UI.

Dane potrzebne do uruchomienia (od właściciela)

  • Działalność gospodarcza / firma + konto u operatora płatności (weryfikacja KYC).
  • Numer konta firmowego do wypłat.
  • Klucze API operatora (test + produkcja) i sekret webhooka.
07

Dostawa — InPost, kurier, odbiór

Trzy metody zgodnie z prototypem. Koszty i progi konfigurowalne w panelu.

MetodaCzasKoszt (przykład)Integracja
Paczkomat InPost1–2 dni robocze12 złInPost ShipX API — widget wyboru paczkomatu (Geowidget), automatyczna etykieta.
Kurier (DPD / InPost)1–2 dni robocze16 złInPost / DPD API lub agregator Furgonetka / BaseLinker.
Odbiór osobistypo umówieniu0 złBrak integracji — kontakt telefoniczny/mailowy, status ręczny w panelu.

Uwagi wdrożeniowe

  • Darmowa dostawa od progu (w prototypie: 150 zł) — logika po stronie /api/checkout/quote.
  • Geowidget InPost do wyboru paczkomatu — zwraca kod punktu zapisywany w ShippingAddress.parcelLockerCode.
  • Pakowanie produktu szklanego — uwzględnić w opisie zamówienia (ostrożnie, miód = szkło). Nie wpływa na kod, ale na proces.
  • Numer śledzenia z API zapisujemy w zamówieniu i wysyłamy klientowi e-mailem.
08

Panel administracyjny i CMS

Właściciel pasieki musi obsłużyć sklep samodzielnie, bez programisty. Prosty, czytelny panel.

Funkcje panelu

  • Zamówienia — lista, szczegóły, zmiana statusu (nowe → opłacone → spakowane → wysłane → zrealizowane), wydruk etykiety, numer śledzenia.
  • Produkty i magazyn — edycja odmian, wariantów, cen, opisów; stany magazynowe z ostrzeżeniem o niskim stanie; włączanie/wyłączanie produktu (np. sezonowy miód wrzosowy).
  • Treści — wpisy bloga „Dziennik", zdjęcia galerii, sekcja „O nas".
  • Opinie — moderacja i zatwierdzanie recenzji.
  • Newsletter — eksport adresów lub integracja z MailerLite/Brevo.
CMS bez kodu: dla bloga i edytowalnych treści warto użyć gotowego CMS (Sanity / Payload) — właściciel dodaje wpisy i zdjęcia przez przyjazny interfejs, a programista nie jest potrzebny do codziennej obsługi.
09

Wymogi prawne (RODO, sprzedaż żywności)

Sklep sprzedaje żywność konsumentom w Polsce — obowiązują przepisy e-commerce, RODO oraz wymogi dla produktów spożywczych. Poniżej lista do wdrożenia (skonsultować z prawnikiem/księgowym).

  • Regulamin sklepu i Polityka prywatności — wymagane, dostępne ze stopki (linki już w prototypie).
  • Zgody i RODO — checkboxy zgód (regulamin, przetwarzanie danych, newsletter), informacja o administratorze danych, prawo do usunięcia.
  • Prawo odstąpienia — uwaga: żywność łatwo psująca się / o krótkim terminie może być wyłączona z prawa zwrotu; jednoznacznie określić w regulaminie.
  • Etykieta produktu spożywczego — skład, masa netto, dane producenta, warunki przechowywania, kraj pochodzenia, numer partii. Dane wyświetlane na stronie produktu i na słoiku.
  • Cookies — baner zgody na pliki cookie / analitykę.
  • Faktury / paragony — integracja z systemem fakturowym lub kasą online (zależnie od formy działalności).
Zastrzeżenie: powyższe to lista techniczna do uwzględnienia w implementacji, nie porada prawna. Treść regulaminu i zakres obowiązków podatkowych należy potwierdzić z prawnikiem i księgowym.
10

SEO, wydajność, analityka

  • SSR/SSG stron produktowych i bloga (Next.js) — szybkie ładowanie i indeksacja.
  • Dane strukturalne Product, Offer, AggregateRating, Article (Schema.org / JSON-LD).
  • Meta i Open Graph dla każdego produktu i wpisu; sitemap.xml i robots.txt.
  • Optymalizacja zdjęć (WebP/AVIF, lazy-loading) — kluczowe dla marki opartej na zdjęciach.
  • Analityka — Google Analytics 4 lub Plausible (prywatność); zdarzenia e-commerce (dodanie do koszyka, zakup).
  • Wydajność — cel Lighthouse ≥ 90; Core Web Vitals w zielonych zakresach.
